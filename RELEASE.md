# Выпуск an-Nur в App Store

**TL;DR.** Версия `1.2 (4)` собрана, проверена и разложена в нативные проекты.
Всё, что можно проверить без macOS, проверено: 35/35 предполётных проверок,
220 тестов, сакральный гард. Осталось три действия на Mac: `Archive`, `Upload`,
отправка на ревью. Остальное можно снять с человека, дав ключ App Store Connect
API — см. раздел «Доступ к App Store Connect».

---

## Почему часть работы нельзя сделать удалённо

Разделение жёсткое и не обходится доступами:

| Что | Где выполняется | Почему |
|---|---|---|
| Сборка веба, тесты, гарды, `cap sync`, предполётная проверка | где угодно, в том числе на сервере | обычный Node |
| **Сборка и подпись `.app`/`.ipa`** | **только macOS** | нужен Xcode: он существует только под macOS |
| **Загрузка сборки в App Store Connect** | **только macOS** | Xcode Organizer либо Transporter |
| Метаданные карточки, скриншоты, выбор сборки, отправка на ревью, TestFlight | где угодно | App Store Connect API |

То есть порядок всегда один: **Mac загружает сборку → всё остальное можно
доделать удалённо.** Пароль Apple Account этого не меняет и не запрашивается:
по правилам проекта (`CLAUDE.md`, §0.2) пароль, коды 2FA и recovery key не
просят и в репозитории не хранят. Нужен другой, узкий и отзываемый доступ —
ключ API, см. ниже.

## Шаги на Mac

Предполагается, что репозиторий на Mac синхронизирован с этим состоянием.

**1. Прогнать полную проверку.** Одна команда делает всё: тесты, сакральный
гард, сборку, `cap sync` и предполётную проверку.

```bash
npm run ios:release-check
```

Ожидаемый хвост вывода — `35/35 проверок пройдено`. Если что-то красное,
дальше не идти: именно это и должен ловить гард.

**2. Открыть проект.**

```bash
open ios/App/App.xcodeproj
```

**3. Архив.** В верхней панели выбрать назначение `Any iOS Device (arm64)` —
не симулятор, иначе пункт Archive неактивен. Затем `Product → Archive`.

**4. Загрузка.** Открывшийся Organizer → выбрать свежий архив → `Distribute App`
→ `App Store Connect` → `Upload`. Дождаться, пока Apple обработает сборку
(обычно минуты, иногда до часа) — до этого она не появится в списке.

**5. Отправка на ревью.** В App Store Connect создать версию `1.2`, выбрать
обработанную сборку `1.2 (4)`, вставить «Что нового» из `APP_STORE.md`,
отправить. Этот шаг можно снять с человека — см. следующий раздел.

Архив полезно сохранить рядом с прошлыми: `app-store/archive/`. В git он не
попадёт — каталог в `.gitignore` как артефакт сборки (каждый весит за 200 МБ).

## Доступ к App Store Connect

Ключ API даёт вести карточку и отправлять сборку на ревью удалённо. Он **не**
даёт собирать приложение — шаги 1–4 выше остаются за Mac.

### Как выпустить ключ

1. App Store Connect → **Users and Access** → вкладка **Integrations** →
   **App Store Connect API** → **Team Keys**.
2. Кнопка **+**, имя произвольное (например `an-Nur release`).
3. Роль — **App Manager**. Этого достаточно для метаданных, выбора сборки и
   отправки на ревью. `Admin` и `Account Holder` не нужны: чем уже права, тем
   меньше цена ошибки.
4. Скачать файл `AuthKey_XXXXXXXXXX.p8`. **Apple даёт скачать его один раз.**
5. Записать рядом два значения с той же страницы: **Issuer ID** (общий на
   команду, вида `69a6de70-…`) и **Key ID** (10 символов, он же в имени файла).

### Что передать

Три вещи: файл `.p8`, Issuer ID, Key ID. Файл кладётся в `secrets/` — каталог
целиком в `.gitignore`, как и любые `*.p8`; проверено, git его не видит.

Пароль Apple Account, коды двухфакторной аутентификации и recovery key
передавать не нужно и нельзя.

### Проверка доступа

Первая команда — только чтение, ничего не меняет:

```bash
ASC_ISSUER_ID=<issuer id> \
ASC_KEY_ID=<key id> \
ASC_KEY_PATH=secrets/AuthKey_XXXXXXXXXX.p8 \
npm run asc:status
```

Она печатает приложения команды, версии и загруженные сборки. Если приложение
`ru.annur.quran` в списке — доступ настроен верно.

### Если ключ скомпрометирован

Отозвать там же, в Integrations, кнопкой **Revoke**. Действует немедленно.
Выпустить новый — минута.

## Что останется сделать после появления доступа

Команды поверх готового клиента (`scripts/appstore/asc-client.mjs`) пишутся
после первой удачной проверки доступа, а не вслепую: состав полей у версий и
сборок Apple меняла не раз, часть атрибутов помечена deprecated. Поэтому
`asc:status` печатает атрибуты **как есть** — по её выводу видно фактические
имена полей, и уже на них строятся команды правки. Писать их сейчас наугад
означало бы выдумывать имена эндпоинтов, чего делать нельзя.

Порядок работ, когда ключ появится:

1. `npm run asc:status` — убедиться, что доступ есть и приложение видно.
2. По фактическому ответу дописать команду обновления «Что нового» и выбора
   сборки.
3. Отправка на ревью — последним шагом, отдельной командой с явным
   подтверждением: это действие видно снаружи и его нельзя отменить незаметно.

## Чего ещё не хватает для Submit

Эти пункты — не код, они требуют решений владельца. Полный список —
`APP_STORE.md`, § «Блокеры перед Submit for Review».

- Реальные ФИО или название правообладателя и рабочий e-mail в юридических
  документах вместо старого домена `quraning.app`.
- Сохранённые лицензии и разрешения на перевод, аудио и тайминги.
- Подтверждение, как внешние аудио-CDN хранят IP и технические логи — от этого
  зависит ответ в разделе App Privacy.
- TestFlight-прогон на физическом iPhone и iPad.
