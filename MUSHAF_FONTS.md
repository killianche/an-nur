# Шрифты мусхафа: как это устроено и что нельзя ломать

**TL;DR.** Текст мусхафа рисуется не буквами, а готовыми глифами-словами из
приватной области Unicode. Слово задаётся **парой** «PUA-код + шрифт», а после
нарезки — **тройкой** «код + шрифт + страница». Ошибка в этой связке не падает
и не подсвечивается: на экране будет красивый арабский, просто **не тот**.

**Имя для запроса:** «шрифты мусхафа», «постраничные шрифты», «почему кубики»,
«перегенерировать шрифты».

---

## Что где лежит

| Путь | Что это |
|---|---|
| `vendor/qcf4-fonts-woff2/` | 48 исходных шрифтов QCF V4 от King Fahd Complex, ~780 КБ каждый. **Вне `public`** — в рантайме не нужны, в пакете были лишними 36 МБ. Нужны, чтобы повторить нарезку. |
| `public/qcf4/fonts-page/NNN/FONT.woff2` | 797 постраничных подмножеств, ~71 КБ на страницу. Это то, что реально качает приложение. |
| `public/qcf4/pages/NNN.json` | Данные страницы: строки, слова, для каждого слова `char` (PUA-глиф) и `font`. |
| `scripts/build-page-fonts.py` | Генератор подмножеств с двойной проверкой. |

## Как перегенерировать

```bash
python3 scripts/build-page-fonts.py
```

Требует `fontTools` и `brotli`. Идемпотентен: свежие файлы пропускает.
Отдельные страницы — `python3 scripts/build-page-fonts.py 77 90`.
Только проверить готовое — `python3 scripts/build-page-fonts.py --check`.

## 🔴 Обязательный порядок после правки данных мусхафа

Если менялись `public/qcf4/pages/*.json` или исходные шрифты:

1. `python3 scripts/build-page-fonts.py` — перегенерировать подмножества.
2. `npm test` — группа «Шрифты мусхафа: подмножества сгенерированы полностью»
   проверит, что для каждой страницы есть ровно те файлы, которые она просит.
3. `npm run build`
4. **`npx cap sync`** — иначе в iOS и Android останутся старые файлы.
5. Проверить на симуляторе, что арабский виден.

**Шаг 4 однажды уже забыли.** В `ios/` и `android/` лежали старые 48 шрифтов, а
постраничных не было вовсе: код просил `/qcf4/fonts-page/NNN/`, и на телефоне
аяты остались бы пустыми навсегда. В вебе всё работало — проблема видна только
в нативной сборке.

## Три правила, которые нельзя нарушать

### 1. Семейство обязано нести номер страницы

```ts
qcfPageFamily('QCF4_Hafs_06', 77)  // → 'QCF4_Hafs_06_p77'
```

QCF V4 переиспользует одни и те же PUA-коды в разных шрифтах: `0xF103` в
`Hafs_01` и в `Hafs_06` — **разные слова**. Подмножества одного шрифта для
разных страниц тоже пересекаются по кодам.

Если назвать их одинаково, браузер сложит все `@font-face` с этим именем в одно
семейство и на пересекающемся коде отдаст глиф не той страницы — **чужое слово
внутри аята**. Ни типы, ни сборка этого не увидят.

Поэтому же у слова есть поле `page`: его проставляет `hydratePage` при загрузке.
Аят на стыке страниц берёт слова с двух — одного номера на аят не хватает.

### 2. Кубики недопустимы

У PUA-кодов нет запасного глифа ни в одном системном шрифте. «Показать текст,
пока шрифт не приехал» означает ряды пустых квадратов на месте аята — это
выглядит как испорченный Коран.

Поэтому текст рисуется **только** после подтверждённой загрузки
(`useQcfFont` → `ready`), а до этого на его месте `ArabicSkeleton`. Если
загрузка не удалась — `FontErrorBanner` с повтором, но не текст.

`font-display: block` в правиле остаётся страховкой: пустая строка лучше кубиков.

### 3. Готовность шрифта проверяется по статусу FontFace

```ts
const ok = faces.length > 0 && faces.every(f => f.status === 'loaded');
```

**Не через `document.fonts.check(...)`.** Без второго аргумента `check()`
спрашивает, нарисуется ли **пробел**, а в подмножестве страницы бывает
один-единственный PUA-глиф без пробела. Загруженный шрифт считался бы
сломанным, и плашка об ошибке висела бы над живым текстом.

## Почему нарезали по страницам

QCF V4 раздаётся 48 файлами по ~780 КБ, каждый содержит 2073 глифа. Странице
нужно около 140 из них. На открытие уходило в среднем 0.89 МБ, местами 1.78 МБ.
Худший случай — служебные шрифты: страница 77 тянула `QCF4_Hafs_01` весом
924 КБ **ради одного глифа** с названием суры.

После нарезки: 2.26 МБ → 84 КБ (3.6%). Время до арабского на живом сервере —
0.8–2 с вместо 10–20.

## Почему это безопасно для сакрального текста

Сабсеттинг не рисует и не меняет глифы — он выбрасывает из бинарника
неиспользуемые. Формы букв остаются те же байты, что дал King Fahd Complex.

«Должно быть безопасно» для мусхафа не годится, поэтому генератор проверяет
каждую страницу дважды и падает при первом расхождении:

1. **Покрытие** — cmap подмножества содержит все коды, которые есть на странице.
2. **Тождество** — контур и ширина каждого глифа сверяются с оригиналом по хешу
   записи пера.

Прогон по всем 604 страницам: расхождений нет. Дополнительно сверено в браузере —
16 слов с 4 разных страниц отрисованы подмножеством и оригинальным шрифтом,
ширина и высота совпадают до сотых.

## Что ещё держит скорость

Эти вещи легко случайно откатить, поэтому они перечислены здесь:

- **Шрифт просят только аяты вблизи экрана** (`useNearViewport`). Сура
  монтируется целиком, и без этого Ан-Ниса разом запрашивала 32 подмножества —
  файл первого экрана приходил вместе с последними.
- **Первые `EAGER_AYAHS` от места чтения просят сразу**, минуя наблюдатель:
  при монтировании длинной суры его вердикт приходил через две секунды **после**
  того, как шрифт уже загрузился.
- **Шрифт первой страницы заказывается до готовности ленты** — номер страницы
  известен из таблицы `mushafPages` без сети.
- **Лента отдаёт начало суры**, не дожидаясь остальных страниц (только когда
  читают сверху).
- **Датасет альтернативных начертаний (3.9 МБ) не качается**, пока выбран
  мусхаф. Раньше тянулся при каждом открытии суры и забивал канал.
- **Соседние страницы мусхафа предзагружаются** — перелистывание без скелета.

## Кэш на сервере

Правила в `/etc/caddy/Caddyfile`, блок `l.asrbook.ru`: кэш по **расширению**,
а не по папке. Раньше правила покрывали только `/assets`, `/fonts`, `/audio`, и
шрифты мусхафа уходили вообще без `Cache-Control` — браузер перекачивал их при
каждом открытии суры.

Две грабли, на которые уже наступили:

- **Матчеры Caddy соединяют `path` через И, а не ИЛИ.** Несколько строк `path`
  в одном именованном матчере дают невыполнимое условие. Все расширения — одной
  строкой.
- **Правку якорить по границам блока сайта**, а не по первому совпадению текста:
  на сервере несколько сайтов с одинаковыми правилами, и патч ушёл не туда.
  Проверять `caddy adapt`, а не только `caddy validate`.
